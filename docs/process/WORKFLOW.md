# 《墨卷三国》研发流程

## 角色
| 角色 | 负责 | 产出 |
|---|---|---|
| 用户（制作人） | 方向、设计决策、最终拍板 | 需求、决策 |
| Grok Bot（项目负责人） | 拆任务、分发、验收、汇报 | 任务单、验收结论 |
| PRD 文档助手（策划） | 维护 PRD，记录决策 | docs/PRD.md、docs/CHANGELOG.md |
| UI 设计助手 | 界面布局、视觉规范、交互稿 | docs/ui/ 规范与稿件、样式代码 |
| 研发助手 | 功能实现、重构、单测 | 分支 + PR |
| 测试助手 | 测试用例、回归、试玩与数值反馈 | 测试报告、Bug issue |

## 任务流
1. 需求：用户提出 → 负责人判断是否涉及规则；涉及规则先交 PRD 助手更新 PRD（冲突时问用户）。
2. 拆解：负责人在 GitHub 建 issue（标签：`prd` / `ui` / `dev` / `qa`），写明目标、PRD 章节、验收标准。
3. 执行：对应助手认领，按 `feat/<issue号>-简述` 建分支，完成后开 PR，PR 描述引用 issue 与 PRD 章节。
4. 测试：测试助手在 PR 的 Pages 预览或本地构建上回归，结果写在 PR 评论。
5. 验收：负责人对照验收标准检查（CI 绿、测试通过、截图/试玩确认），通过后合并到 main，自动部署到线上。
6. 汇报：负责人向用户汇报结果与线上链接，需要决策的点集中提问。

## 规则
- main 只接受 PR 合并，CI（lint + test + build）必须为绿。
- 规则以 docs/PRD.md 为准；代码与 PRD 不一致时先改 PRD 再改代码。
- 每个 PR 只做一件事；数值改动放 src/data，不写死在逻辑里。
- 设计决策写入 docs/CHANGELOG.md。
- 助手之间不直接改对方负责的文件，需要时通过负责人或 issue 协调。
